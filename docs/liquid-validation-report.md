# Liquid 개선 후 추가 검증

2026-10-31 작업 트리의 추가 검증 기록. 설치된 앱이나 릴리스를 변경하지 않고 `com.tokenusage.notch-preview`에서 실행했다.

**판정: 일반 화면 사용과 배치·복구 검증은 양호하지만, 연속 화면 녹화/공유까지 완성됐다고 판단할 수 없다.** 동적 배경에서 외부 캡처에 노치가 간헐적으로 빠지는 현상이 재현됐다. CPU 비용 역시 동적 반응성과의 절충이므로 모든 조건에서 더 가볍다고 주장하지 않는다.

## hover 실패 원인과 수정

`native-quality-smoke.py`의 합성 `pointerenter`는 OS 커서를 움직이지 않았다. 설정 패널을 닫은 직후 기존 커서 위치에서 실제 `pointerleave`가 뒤늦게 발생했고, 제품의 정상적인 180ms 닫기 지연이 상세를 닫았다.

실패 재현에서는 Liquid 상세가 2511ms에 열려 있었고, 실제 `pointerleave`가 2526ms에 발생한 뒤 2713ms에 닫혔다. 동작을 없애거나 지연을 늘리지 않고 테스트가 실제 커서를 셀 안으로 이동하도록 수정했다. 45개 관측 프레임 모두 상세가 열려 있어야 한다는 검증도 추가했다.

수정 후 Dark·Glass·Liquid 모두 통과했다. 세 테마의 설정 탭 높이는 각각 `[440, 440, 440]` DIP였으며 네이티브 창·노치 위치가 유지됐다.

## CPU·프레임 콜백 비교

비교 기준은 `b5fa7c2642cf107dd15dc3e8cde3ac6ec6e1401a`의 `liquid-glass.ts`와 `liquid-loop.ts`다. 기존 렌더러의 외부 이벤트 진입은 no-op으로 연결했다. 현재 네이티브 백엔드·이벤트 훅·비활성 파일 로그는 양쪽에서 공유한다. 따라서 **렌더러 경로의 A/B이며 이전 릴리스 전체와의 A/B가 아니다.**

- 순서: baseline → current → current → baseline.
- 표본: 각 정적/창 이동/픽셀 변화 조건 약 8초, 조건별 2회.
- 범위: 디버그 Tauri 프로세스와 WebView2 자식 프로세스 7개. 12 logical CPU로 정규화.
- 실제 GDI 캡처 사용. 배경은 작은 단색 테스트 창이며 동적 조건은 약 65ms 간격으로 색상을 변경했다.
- rAF 횟수는 계측 이후 페이지에서 실행된 콜백이며 OS wakeup 또는 compositor present FPS가 아니다.
- CPU 평균은 아래 두 표본의 산술 평균이다. 백그라운드 앱을 전부 정지한 실험실 측정이 아니다.

| 조건 | 이전 CPU, 전체 머신 % | 현재 CPU, 전체 머신 % | 이전/현재 rAF 약 8초 | 이전/현재 변경 그리기 약 8초 |
| --- | ---: | ---: | ---: | ---: |
| 정적 배경 | 0.325 | 0.248 | 1,157 / 10 | 0 / 0 |
| 창 이동 + 색상 변화 | 0.513 | 3.181 | 1,157 / 384 | 6 / 110 |
| 픽셀만 변화 | 0.751 | 2.415 | 1,160 / 397 | 6 / 104 |

정적 상태의 불필요한 콜백 감소는 명확하다. 그러나 CPU 표본 편차가 크고 추가 GPU 수집 세션의 정적 CPU는 이전 0.294%, 현재 0.355%로 방향이 뒤집혔다. **일관된 CPU 절감률을 입증했다고 해석하지 않는다.**

동적 배경에서는 이전의 약 1fps 추적보다 더 많은 변경을 반영하므로 CPU 비용이 증가한다. 현재 구현은 모든 상황에서 더 저렴한 것이 아니라, 정적 콜백 낭비를 줄이고 동적 반응성을 높이는 절충이다.

## GPU·전력 계측 한계

Windows `Win32_PerfFormattedData_GPUPerformanceCounters_GPUEngine`을 조회했다. 대상 프로세스에 대응하는 엔진 행은 27개였으나, 별도 A/B 세션의 조건별 5개 표본이 모두 0이었다. 카운터의 분해능·귀속 범위로 인해 유의미한 차이를 관찰하지 못했으며, GPU 사용이 없다는 의미가 아니다. DWM 등 공유 compositor 비용을 앱 프로세스에 완전히 귀속하지 못했다.

배터리 계측 정보와 외부 전력 측정기가 없어 전력·배터리 절감은 정량 검증하지 않았다.

## 환경·복구·자원 관찰

실제 모니터는 2560×1440과 1024×1280 두 대이며 둘 다 배율 100%였다. 두 모니터 각각 상·하·좌·우, 총 8개 배치에서 Liquid 준비 상태와 설정 패널의 화면 내 위치를 확인했다. 탭 전환 중 HWND 위치와 패널 높이는 일정했다. 큰 모니터의 설정 높이는 440 DIP, 작은 모니터는 421 DIP였다.

10회 페이지 재로드 후 모두 Liquid가 준비 상태로 복귀했다. 이어 약 180.85초 동안 관찰한 결과:

| 항목 | 결과 |
| --- | --- |
| Canvas 수 | 2개로 유지 |
| DOM 노드 수 | 304개로 유지 |
| JS heap | 약 11.58→13.95 MiB, 최저 약 11.55 MiB |
| 앱+WebView2 private bytes 합계 | 약 442.01→320.25 MiB |
| 핸들 합계 | 3,609→3,593 |
| 프로세스 수 | 7개로 유지 |
| 페이지 오류 | 0개 |

이 짧은 관찰에서 DOM·Canvas·핸들의 지속 증가를 보지 못했다. JS heap의 변동은 GC 주기 등을 포함하며 이 표본만으로 누수 유무를 단정하지 않는다. 수 시간 사용, 실제 절전/복귀, 모니터 케이블 분리, 실제 DPI 변경은 검증하지 않았다. 재로드 검증을 OS 절전 복귀 검증으로 대신 표기하지 않는다.

## 반영 지연과 화면 캡처에서 발견한 제약

실제 배경 창 이동·색상 변경 20회 표본을 두 번 실행했다. 첫 표본 p50/p95는 30/31ms, 재실행은 29/31ms였다. 이것은 Canvas 그리기까지의 지연이며 화면에 표시되는 순간의 지연이나 모든 환경의 보장값이 아니다.

연속 변화 중 layered window를 포함하는 OS 스크린샷을 20회씩 수집했다. 단색 배경에 노치가 보이면 여러 색상으로 나타나는 것을 판별하고, 대표 이미지를 직접 확인했다.

- 첫 실행: 20개 중 11개에서 노치가 빠짐.
- 재실행: 20개 중 8개에서 노치가 빠짐.
- `tmp/liquid-sharing-visible.png`: 노치가 포함된 표본.
- `tmp/liquid-sharing-absent.png`: 같은 영역에 배경만 남은 표본.
- 정지 후 명시적 해제 상태의 스크린샷에서는 정상 표시됨.

현재 `WDA_EXCLUDEFROMCAPTURE`는 자신의 배경 읽기뿐 아니라 다른 캡처에도 영향을 준다. 묶음 완료 후 해제는 무기한 제외를 막지만, 다른 도구가 짧은 제외 구간에 읽는 것까지 막지는 못한다. **자기 배경 캡처와 외부 녹화가 동시에 실행될 때의 간헐적 누락은 남은 제품 제약이다.** 단순한 테스트 HWND 선택 오류는 이번 최종 검사에서 배제했다.

실제 화상회의로 화면을 외부에 전송하지는 않았다. 위 결과는 로컬 OS 캡처 경로에서의 증거이며, 모든 화면 공유 도구의 동일한 누락률을 뜻하지 않는다. 공유 화면에 노치가 항상 보여야 한다면 전역 캡처 제외에 의존하는 배경 획득 방식부터 재검토해야 한다. 타이머나 해제 지연만 바꾸는 것으로 완전 해결됐다고 판단하지 않는다.

## 재현 명령

Vite 1524, 별도 Tauri preview의 CDP 9223을 사용한다. preview 구성은 [windows-dev.md](windows-dev.md)를 따른다.

```powershell
python -X utf8 scripts/native-quality-smoke.py --port 9223
python -X utf8 scripts/liquid-native-benchmark.py --baseline-ref b5fa7c2642cf107dd15dc3e8cde3ac6ec6e1401a
python -X utf8 scripts/liquid-native-benchmark.py --baseline-ref b5fa7c2642cf107dd15dc3e8cde3ac6ec6e1401a --gpu
python -X utf8 scripts/liquid-environment-smoke.py --seconds 180
python -X utf8 scripts/liquid-events-native-smoke.py --screenshots --latency-samples 20
```

네이티브 검사는 커서·preview 배치·작은 배경 테스트 창을 사용하므로 서로 동시에 실행하지 않는다. 벤치마크는 자체적으로 기준 코드를 `tmp/liquid-baseline`에 생성한다. 실제 시간 간격은 성능 관측용이며 제품 단위 테스트는 가상 시간을 사용한다.

원시 결과는 `tmp/native-quality-results.json`, `tmp/liquid-native-benchmark.json`, `tmp/liquid-native-gpu.json`에 저장했다. 최초 CPU/GPU 결과는 자동 기준 생성 옵션을 넣기 전에 동일한 기준 파일을 수동 생성해 측정한 것이다.

환경 결과는 `tmp/liquid-environment-results.json`, 최종 지연·외부 캡처 결과는 `tmp/liquid-events-native-results.json`에 있다. 이번 후속 작업은 검증 스크립트와 문서를 보완했으며 제품 캡처 엔진은 변경하지 않았다.
